## 구현 과정

1. 기존 movie 프로젝트의 5주차 회원 중복 조회, 회원별 평점 조회 API를 확인했다.
2. 회원가입/평점 요청 DTO에 Bean Validation을 적용하고 Controller의 @Valid로 검증했다.
3. spring-security-crypto만 추가해 로그인 자동 설정 없이 BCryptPasswordEncoder를 등록했다.
4. 회원가입 서비스에서 이메일/닉네임을 확인하고 bcrypt로 해시한 비밀번호를 저장했다. 응답 DTO에는 회원 ID·이메일·닉네임만 담았다.
5. 평점 등록은 회원 존재 여부와 중복 여부를 확인했다. 수정/삭제는 평점 조회 후 소유자를 비교했다.
6. RestControllerAdvice에서 400/403/404/409를 공통 ApiResponse로 반환했다.
7. DB UNIQUE/FK를 서비스와 별도로 점검하고 H2 통합 테스트로 실제 제약 위반을 확인했다.
8. Postman 요청 모음을 만들었다. 실제 MySQL 실행과 요청/응답 캡처는 아래에 추가한다.

## 실제 트러블슈팅 1건: Gradle 캐시 위치 오류

**이슈**

처음 `gradlew.bat test` 실행 시 테스트가 시작되기 전에 아래 오류가 발생했다.

```text
Could not create parent directory for lock file C:\.gradle\wrapper\dists\gradle-9.8.2-bin\...\gradle-9.8.2-bin.zip.lck
```

**문제**

해당 실행 환경에서 Gradle 사용자 홈이 C:\.gradle로 해석됐고, 해당 위치에 잠금 파일 디렉터리를 생성하지 못했다. API 코드 실패가 아니라 Gradle 실행 환경 문제였다.

**해결**

이미 설치된 배포 파일과 캐시가 있는 사용자 Gradle 홈을 명시했다.

```powershell
.\gradlew.bat --gradle-user-home C:/Users/checkup/.gradle test --console=plain
```

테스트가 실행됐고 전체 테스트가 통과했다. 실제 실행 결과는 로컬 `build/reports/tests/test/index.html`에서 확인할 수 있다. 다른 컴퓨터에서는 해당 사용자의 Gradle 홈으로 경로를 바꾼다.

**근거**

실제 Gradle 실행 오류와 테스트 실행 결과. 외부 참고 문서는 사용하지 않았다.

## 선택 Challenge 설명

서비스가 이메일/닉네임 중복 여부를 검사한 뒤 다른 요청이 먼저 저장할 수 있다. 따라서 사전 검사만으로는 중복 저장을 완전히 막을 수 없으며 DB UNIQUE 제약이 필요하다. 사전 검사는 이메일 MEMBER4091, 닉네임 MEMBER4092로 구분하고, 최종 DB 제약 위반은 COMMON4091의 공통 오류 응답으로 변환했다.

자동 테스트는 사전 조회만 false로 고정한 뒤 실제 H2 DB 저장을 실패시키는 방식으로 이 상황을 검증했다. 실제 MySQL 동시 요청 캡처를 했다는 의미는 아니다. 선택 미션 제출 시 해당 캡처를 별도로 추가한다.

## 학습 후기 초안 — 본인 경험에 맞게 수정

DTO 검증은 입력 형식과 범위를 확인하고, 서비스는 회원 존재 여부와 평점 소유권 같은 업무 규칙을 확인하며, DB 제약은 최종 저장 단계에서 중복과 잘못된 참조를 막는다는 역할 차이를 정리했다. 공통 응답 구조를 사용하면 프론트에서 성공 여부와 오류 메시지를 같은 방식으로 처리할 수 있다. 비밀번호를 해시로 저장하는 것뿐 아니라 응답 DTO에서 아예 제외하는 것도 필요하다. 동시 요청에서는 사전 중복 조회를 통과할 수 있으므로 UNIQUE 제약을 함께 두어야 한다.
