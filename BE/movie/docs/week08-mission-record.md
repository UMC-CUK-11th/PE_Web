# 8주차 미션 기록

1. 기존 즐겨찾기 코드와 MySQL 스키마를 확인했다. Favorite는 BaseTimeEntity를 상속하고 회원 ID와 영화 ID의 조합을 유일하게 유지한다.
2. JWT에서 얻은 회원 ID로 즐겨찾기를 등록·조회·해제하도록 확인했다. 다른 회원 토큰으로 같은 영화를 조회하면 false, 해제를 시도하면 404가 반환된다.
3. 영화 기록 서비스의 트랜잭션에서 기존 평점 저장 서비스를 먼저 호출하고, addToFavorites가 true일 때 즐겨찾기 저장을 호출했다. false면 평점만 저장하며 응답의 favorite가 null이다.
4. 한 영화에 기존 즐겨찾기를 만들어 둔 뒤 영화 기록 저장을 호출했다. 409 후 내 평점 목록에 해당 영화가 없고 기존 즐겨찾기는 그대로였다.
5. 테스트에서 중복 사전 조회만 오래된 결과로 가정했다. 실제 INSERT가 DB UNIQUE 제약에 걸렸고, 같은 요청에서 먼저 저장한 평점이 남지 않았음을 확인했다.
6. Swagger에 공개 로그인과 토큰이 필요한 다섯 작업, 요청과 성공·실패 예시를 기록했다.

## 검증 기록

- Spring Boot/JUnit/H2 통합 및 회귀 테스트 50개 통과.
- 실행 중인 H2 서버에 실제 HTTP 요청 25개 통과. 두 계정 격리, 정렬, 빈 목록, 입력 오류, 중복 및 롤백을 확인했다.
- 실제 DB UNIQUE 위반은 409 COMMON4091, 정상적인 즐겨찾기 사전 검사에서는 409 FAVORITE409_1이다.

## 트러블 슈팅

- 이슈. 첫 Swagger UI 요청이 404였다.
- 문제. springdoc의 API 문서 자동 설정을 끄는 속성이 Swagger UI 초기화에도 영향을 줬다.
- 해결. 자동 설정을 활성화하고 Swagger UI가 8주차 명세 파일을 사용하도록 설정했다. [springdoc 공식 문서](https://springdoc.org/v2/)

## 학습 후기 초안

평점 INSERT가 이미 실행됐더라도 그 트랜잭션 안에서 즐겨찾기 저장이 실패하면 변경을 취소할 수 있다는 점이 인상적이었다. 사전 조회는 원인을 쉽게 설명해 주고 DB UNIQUE는 두 요청이 동시에 들어와도 중복을 막아 준다. 두 검사를 같이 두는 이유가 서로 다르다는 것을 실패 응답과 DB 상태로 확인했다.
