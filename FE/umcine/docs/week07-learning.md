# 7주차 핵심 개념 정리

## 인증과 인가

인증은 요청자가 누구인지 확인하는 과정이다. 예를 들어 서버가 이메일과 비밀번호를 확인하고 계정 소유자를 식별한다. 인가는 그 사용자가 어떤 작업을 할 수 있는지 판단하는 과정이다. 로그인을 했더라도 다른 회원의 평점을 수정할 수 없는 것이 예다. 화면에서 버튼을 숨겨도 HTTP 요청을 직접 보낼 수 있으므로 실제 권한은 서버에서도 확인해야 한다. [OWASP 인증](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP 인가](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

이번 `/login`은 입력 화면이고 실제 인증은 하지 않는다. `/mypage`는 예시 데이터의 퍼블리싱 화면이므로 실제 로그인한 사용자의 정보가 아니다. 실제 토큰 발급/검증과 회원 정보 연동은 후속 주차 범위다.

## JWT

워크북에서 다루는 서명된 JWT(JWS compact)는 `header.payload.signature` 세 부분이다. header는 토큰 유형과 알고리즘 정보를, payload는 sub(주체)·exp(만료 시각) 같은 클레임을 담는다. signature는 합의한 알고리즘과 키로 생성하며, 서버가 발급자 및 변조 여부를 확인하는 데 사용한다. JWT에는 암호화 형태도 있지만 이번 워크북의 서명된 JWT는 내용을 숨기지 않는다. [RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519)

디코딩은 Base64url로 표현된 내용을 읽는 과정일 뿐, 토큰이 유효하다는 뜻이 아니다. 검증은 서명과 허용 알고리즘, 만료 시각 및 서비스가 요구하는 발급자·대상 같은 클레임을 확인하는 과정이다. 읽을 수 있는 payload에 비밀번호를 담지 않는다.

JWT가 있다는 이유만으로 모든 요청을 허용하지 않는다. 서버가 검증한 사용자 식별자를 바탕으로 요청한 데이터의 소유권이나 역할을 확인해야 한다.

## 직접 답해 볼 질문

1. 이메일 중복 확인을 통과한 뒤 입력 이메일을 바꾸면 왜 다시 확인해야 할까?
2. 비밀번호 확인 값은 왜 회원가입 API에 보내지 않을까?
3. 두 중복 확인이 성공했는데도 POST /members가 409를 반환할 수 있는 이유는 무엇일까?
4. JWT payload를 읽을 수 있는 것과 서버가 서명을 검증한 것은 어떻게 다를까?
5. 로그인한 회원 A가 회원 B의 평점을 수정할 수 없도록 확인하는 것은 인증일까, 인가일까?
